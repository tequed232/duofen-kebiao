# 协作与表达约定（人 + AI 统一适用）

这份文档是给**参与本项目的任何人/任何模型**看的：写提交信息、写文档、写注释、
以及和 AI 协作时它该如何说明自己的判断过程，一律按这里来。

## 一、语言与语义

- **中文优先**，包括提交信息、文档、代码注释、以及 AI 的思考/判断说明。
- **高语义**：一个词承载尽量多的信息，能一个词说清就不用一句，能一句就不用一段。
  反例："提升了代码质量"、"优化了体验"、"完善了逻辑" —— 这些是零信息量的套话。
- **允许一词多义**：写的人不必每次限定词义，读的人按语境取义。
  例：「玻璃」可能指材质观感 / 那层 SVG 滤镜 / 底栏那圈折射带；「散射」可能指模糊层，也可能指它的观感。
  真要精确到实现时，落到**文件名与变量名**上，而不是靠形容词堆。
- **惜字，但不省事实**：根因、验证方式、影响面、数字（实测帧率、余量 px、文件大小）必须写；
  省掉的是套话与重复叙述。

## 二、参照系：国内成熟开源项目

不确定某个说法是否地道、某类改动该怎么描述时，**去翻这些项目的 PR / CHANGELOG / 文档**，
按它们的落笔方式写：

| 项目 | 可参考的部分 |
| --- | --- |
| [MaaAssistantArknights](https://github.com/MaaAssistantArknights/MaaAssistantArknights) | PR 标题与正文结构、变更说明的颗粒度、"一条 PR 一件事"的实践 |
| [ClassIsland](https://github.com/ClassIsland/ClassIsland) | 面向学生的桌面课表类项目：功能命名、用户向文案、Issue 沟通口吻 |
| [BililiveRecorder](https://github.com/BililiveRecorder/BililiveRecorder) | 中文技术文档的密度与节奏、版本发布说明写法 |

> 不是照抄，是**对齐语感**：同样是中文技术写作，它们读起来是"同行在说话"，而不是翻译腔。

## 三、提交信息

见 [`commit-convention.md`](./commit-convention.md)：`类型(范围): 中文描述`，一条一件事，
正文写「为什么 + 影响面 + 验证」。类型与范围的取值也在那份文档里。

## 四、和 AI 协作时的判断说明

- 说自己的判断时**用中文，说结论 + 依据**，不要复述过程流水账。
- 有实测数据就上数字（"与底栏余量 +16px" 比 "现在能正常显示了" 有用得多）。
- 拿不准作者意图时：**先看仓库里的既有约定与国内同类项目的做法**，再问一个精准的问题；
  不要用一串澄清问题代替自己查证。
- 犯错就直说错在哪：例如"选择器少了一层 `.screen`，规则从未命中" —— 比"已修复相关问题"有价值。

## 五、AI 的思考展示（作者明确要求）

- 思考/推理的展示**用中文**，走"高语义 + 一词多义"的路子：短句、名词化、能省则省。
- 允许用行话与简称（玻璃、散射、色散、撞边、流体拉伸），作者按语境理解。
- 涉及"作者到底想要什么"时，可以**翻国内开源项目的同类实现来对齐理解**，再把结论用中文一句话说清。
